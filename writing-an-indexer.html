Writing an indexer

An indexer writes definitions, references, documentation, and relationships in the SCIP format. The protobuf schema defines the data contract; the SCIP CLI provides validation and snapshot tools.

For protocol questions, use the SCIP issue tracker. The following guide covers implementation and validation; it is not a promise of support for a custom indexer.

Understanding the SCIP protobuf schema

An Index contains metadata and a list of Document records. Each document has a path relative to the project root, occurrences associated with source ranges, and information about defined symbols. An index can also provide documentation for external symbols whose source is not indexed.

An Occurrence can describe syntactic information, such as syntax_kind, and semantic information, such as symbol and symbol_roles. Semantic identity connects a reference to its definition; diagnostics can attach additional information to a range.

Use the schema's comments as the field reference. Existing implementations such as scip-typescript and scip-java show how compiler information maps to SCIP.

See also the SCIP protocol reference for messages, enumerations, and field descriptions.

Importing or generating SCIP bindings

The SCIP repository provides bindings for several languages. Importing these avoids maintaining your own protobuf-generation toolchain. Alternatively, vendor the schema and generate bindings yourself when you need control over that process. Test compatibility with the Sourcegraph versions you intend to support.

Generating minimal index with occurrence information

Use a compiler frontend or language server to resolve declarations and references. Traverse the analyzed source, record symbol identities and ranges, then serialize them with the SCIP bindings.

Use index.scip as the default output filename. With scip.proto and the index in the current directory, inspect the protobuf data with:

protoc --decode=scip.Index scip.proto < index.scip

Make the output deterministic. For example, sort entries collected from hash maps before serializing them so repeated runs do not create unrelated snapshot changes.

Snapshot testing with scip CLI

The SCIP CLI's snapshot command annotates source with the occurrences in an index. Check that ranges point to the correct tokens, definitions and references share the intended identities, and package names and versions distinguish external symbols correctly.

For example, this excerpt from a TypeScript index distinguishes a function declaration from a referenced compiler type:

function scriptElementKind(
//       ^^^^^^^^^^^^^^^^^ definition scip-typescript npm @sourcegraph/scip-typescript 0.2.0 src/FileIndexer.ts/scriptElementKind().
  node: ts.Node,
//         ^^^^ reference scip-typescript npm typescript 4.6.2 lib/typescript.d.ts/ts/Node#

Snapshot tests validate the emitted data. Also upload a fixture to Sourcegraph and check its navigation to verify that the data is usable end to end.

Progressively adding support for language features

Navigation capabilities depend on the data emitted: shared symbol identities connect definitions and references, package information enables cross-repository navigation, and explicit relationships enable Find implementations. Hover documentation uses CommonMark; convert other markup before emitting it.

For large indexes, account for protobuf implementation limits: serialized messages must be smaller than 2 GiB. Writing documents incrementally can avoid accumulating the entire index in one message, but each document must still fit. See the scip-ruby streaming example.

Milestone definitions

A valid SCIP file is only the first checkpoint. Test the following behaviors on realistic projects.

Cross-repository identity

Global SCIP symbols encode package identity and version as well as the symbol descriptor; local symbols do not. Emit matching identities for a package's definitions and its consumers' references. Test separately indexed producer and consumer repositories, including two versions of the same package. LSIF uses monikers for the corresponding cross-repository information.

Common build tool integration

Resolve dependencies and generated source using the project's build system. Test a clean checkout as well as a developer's prepared environment so missing build steps are visible.

The long tail: Find implementations

Emit relationships between interfaces, abstract declarations, and concrete implementations. Test language-specific cases such as inheritance, generics, and generated members. A valid index without these relationships cannot provide complete implementation navigation.
